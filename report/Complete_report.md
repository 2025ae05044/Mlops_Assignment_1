## Project overview

This project turns a small tabular classification exercise into a repeatable workflow that can be tested and served as an API. The implementation includes dataset preparation and exploratory analysis, comparison of two classifiers, experiment tracking, a serialized scikit-learn pipeline, a FastAPI service, automated tests, Docker packaging, Kubernetes manifests, and monitoring through Prometheus and Grafana.

The work focuses on the engineering around a model as well as its predictive results: the data preparation steps are in source files, training results are saved, API inputs are validated, and the running service exposes health and metrics endpoints. The classifier is for an educational assignment and must not be used to diagnose or make medical decisions.

## 1. Data acquisition and exploratory analysis

The repository contains the source dataset at `data/raw/processed.cleveland.data` and the prepared file at `data/processed/heart_clean.csv`. Data acquisition and cleaning are handled by `src/data_acquisition.py`; exploratory analysis is generated by `src/eda.py`.

The initial inspection covered 303 records and 14 columns. It found four missing values in `ca` and two in `thal`, with no duplicate rows reported in the inspection. The target was converted to a binary classification value. Missing feature values were retained for handling within the model pipeline rather than being treated as target labels.

The EDA artifacts include class-balance information, feature histograms, and a correlation heatmap. These plots provide a quick check of the target distribution and the relationships and ranges represented in the input data.

## 2. Model development and selection

Two candidate classifiers were evaluated: Logistic Regression and Random Forest. The training workflow is implemented in `src/train.py`. The selected preprocessing and estimator are saved together as a pipeline so that prediction uses the same fitted transformations as training.

The recorded selection criterion was mean cross-validation ROC-AUC. Logistic Regression achieved a mean CV ROC-AUC of **0.902493**, slightly above Random Forest at **0.901712**, so Logistic Regression was selected. On the recorded test split, both models achieved an accuracy of **0.885246**, precision of **0.838710**, and recall of **0.928571**. Logistic Regression achieved a test ROC-AUC of **0.966450**, compared with **0.951299** for Random Forest.

| Metric | Logistic Regression | Random Forest |
|---|---:|---:|
| Mean cross-validation ROC-AUC | 0.902493 | 0.901712 |
| Test accuracy | 0.885246 | 0.885246 |
| Test precision | 0.838710 | 0.838710 |
| Test recall | 0.928571 | 0.928571 |
| Test ROC-AUC | 0.966450 | 0.951299 |

These figures describe the recorded split and experiment only. The difference in cross-validation ROC-AUC is small, and it should not be interpreted as proof that one classifier will always perform better on new data.

The chosen pipeline is stored at `models/best_model_pipeline.joblib`. Other model artifacts and the evaluation files are retained under `models/` and `report/`, including `report/model_comparison.csv` and `report/model_metrics.json`.

## 4. Prediction API and validation

The HTTP service is defined in `src/api.py`, with prediction logic in `src/predict.py`. The API provides:
- `GET /` for basic service information;
- `GET /health` for a health response;
- `POST /predict` for a validated prediction request;
- `GET /metrics/` for Prometheus metrics.

The request schema uses Pydantic and rejects missing, unexpected, or non-numeric feature values. The API also handles prediction errors and a missing model artifact rather than silently returning a normal prediction. Request middleware records the method, path, status code, and elapsed request time.

The prediction output is generated by the saved model pipeline. It is a machine-learning classification result for the assignment, not a clinical assessment.

## 6. Docker and Compose

The Dockerfile packages the application and its Python dependencies into the `heart-disease-mlops:latest` image. The Compose file runs the API together with Prometheus and Grafana. A health check calls the API's `/health` endpoint, allowing the container status to reflect whether the service is responding.

The verified Compose configuration used host port `8002` for the API, `9090` for Prometheus, and `3000` for Grafana. During the lab run, the API health check returned HTTP 200 with a healthy status response. The Prometheus and Grafana services were running alongside the API.

Typical commands for this stack are:

```bash
docker compose up -d --build
docker compose ps
curl -i http://127.0.0.1:8002/health
```

The Grafana credentials in the lab Compose file are demo credentials only. They should be changed before any non-lab deployment.

## 9. Prometheus and Grafana monitoring

The API uses `prometheus-client` to expose application metrics. The custom metric families include:
- `heart_disease_http_requests_total`, a counter labelled by method, endpoint, and status;
- `heart_disease_http_request_duration_seconds`, a histogram of request durations.

The API also exposes Python runtime and process metrics. The file `monitoring/prometheus.yml` configures Prometheus to scrape `heart-disease-api:8000` at the `/metrics/` path every five seconds. The observed Prometheus target response reported the API target as **up**, with an empty last-error field and zero dropped targets.

Grafana was connected to Prometheus and a dashboard was created to visualize request totals, request rate, response time, and a health-related request count. The health-related panel showed the number of health requests; it should not be described as a live availability indicator unless it uses a query such as Prometheus's `up` metric. No alert rules or notification channels were confirmed during the lab work, so this report does not claim that alerting was implemented.

## 10. Architecture and workflow

The workflow starts with the raw Cleveland dataset. The acquisition and EDA scripts prepare and inspect the data. The training script compares classifiers, saves the selected pipeline, and records metrics. MLflow provides a run history. FastAPI loads the saved model for inference, while Docker Compose runs the API and the monitoring services. Prometheus collects request metrics, and Grafana visualizes them. Kubernetes manifests and the GitHub Actions workflow provide deployment and automation configurations.

## 11. Limitations and future improvements

The dataset is small and historical, and the model's test metrics do not establish clinical validity. The evaluation reflects the particular split and recorded experiment. The current lab session also did not have a working Kubernetes profile at the time the monitoring configuration was checked, so the earlier Kubernetes evidence is not a fresh deployment verification.

Possible improvements include exporting the Grafana dashboard as JSON, adding and testing alert rules, adding a smoke test to the container build, documenting a repeatable Kubernetes deployment, and managing non-demo credentials through a secrets mechanism.
